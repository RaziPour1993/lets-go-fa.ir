<div dir='rtl'>در حال حاضر، ما در حال خروجی‌گیری از لاگ‌ها با استفاده از توابع log.Printf() و log.Fatal() هستیم. یک مثال خوب از این، لاگ “شروع سرور…” است که درست قبل از شروع سرور چاپ می‌کنیم:</div>

### افزودن لاگ‌گیری ساختاریافته به برنامه ما

<div dir='rtl'>خوب، بیایید فایل main.go خود را به‌روزرسانی کنیم تا به جای لاگر استاندارد Go از یک لاگر ساختاریافته استفاده کنیم. به این صورت:</div>

<div dir='ltr'>

**File:  cmd/web/main.go**

```

package main

import (
    "flag"
    "log/slog" // New import
    "net/http"
    "os" // New import
)

func main() {
    addr := flag.String("addr", ":4000", "HTTP network address")
    flag.Parse()

    // Use the slog.New() function to initialize a new structured logger, which
    // writes to the standard out stream and uses the default settings.
    logger := slog.New(slog.NewTextHandler(os.Stdout, nil))

    mux := http.NewServeMux()

    fileServer := http.FileServer(http.Dir("./ui/static/"))
    mux.Handle("GET /static/", http.StripPrefix("/static", fileServer))

    mux.HandleFunc("GET /{$}", home)
    mux.HandleFunc("GET /snippet/view/{id}", snippetView)
    mux.HandleFunc("GET /snippet/create", snippetCreate)
    mux.HandleFunc("POST /snippet/create", snippetCreatePost)

    // Use the Info() method to log the starting server message at Info severity
    // (along with the listen address as an attribute).
    logger.Info("starting server", "addr", *addr)

    err := http.ListenAndServe(*addr, mux)
    // And we also use the Error() method to log any error message returned by
    // http.ListenAndServe() at Error severity (with no additional attributes),
    // and then call os.Exit(1) to terminate the application with exit code 1.
    logger.Error(err.Error())
    os.Exit(1)
}

```

</div>

<div dir='rtl'>مهم: هیچ معادل لاگ‌گیری ساختاریافته‌ای برای تابع log.Fatal() وجود ندارد که بتوانیم برای مدیریت خطای بازگشتی از http.ListenAndServe() استفاده کنیم. در عوض، نزدیک‌ترین چیزی که می‌توانیم انجام دهیم این است که یک پیام را در سطح شدت Error لاگ کنیم و سپس به صورت دستی os.Exit(1) را فراخوانی کنیم تا برنامه با کد خروج 1 خاتمه یابد، همانطور که در کد بالا انجام می‌دهیم.</div>

<div dir='rtl'>خوب… بیایید این را امتحان کنیم!</div>

<div dir='rtl'>برنامه را اجرا کنید، سپس یک پنجره ترمینال دیگر باز کنید و سعی کنید آن را برای بار دوم اجرا کنید. این باید یک خطا ایجاد کند زیرا آدرس شبکه‌ای که سرور ما می‌خواهد به آن گوش دهد (":4000") در حال حاضر در حال استفاده است.</div>

<div dir='rtl'>خروجی لاگ در ترمینال دوم شما باید به این صورت باشد:</div>

<div dir='rtl'>این به نظر خوب می‌آید. ما می‌توانیم ببینیم که دو لاگ اطلاعات متفاوتی دارند، اما به همان شکل کلی فرمت‌بندی شده‌اند.</div>

<div dir='rtl'>لاگ اول دارای سطح شدت level=INFO و پیام msg="starting server" است، همراه با ویژگی اضافی addr=:4000. در مقابل، می‌بینیم که لاگ دوم دارای سطح شدت level=ERROR است، مقدار msg حاوی محتوای پیام خطا است و هیچ ویژگی اضافی وجود ندارد.</div>

#### لاگ‌گیری جداشده

<div dir='rtl'>در این فصل، لاگر ساختاریافته خود را تنظیم کرده‌ایم تا لاگ‌ها را به os.Stdout — جریان خروجی استاندارد بنویسد.</div>

<div dir='rtl'>بزرگترین مزیت نوشتن لاگ‌ها به os.Stdout این است که برنامه و لاگ‌گیری شما جدا شده‌اند. خود برنامه شما نگران مسیریابی یا ذخیره لاگ‌ها نیست، و این می‌تواند مدیریت لاگ‌ها را بسته به محیط آسان‌تر کند.</div>

<div dir='rtl'>در طول توسعه، مشاهده خروجی لاگ آسان است زیرا جریان خروجی استاندارد در ترمینال نمایش داده می‌شود.</div>

<div dir='rtl'>در محیط‌های آزمایشی یا تولیدی، می‌توانید جریان را به مقصد نهایی برای مشاهده و بایگانی هدایت کنید. این مقصد می‌تواند فایل‌های دیسک یا یک سرویس لاگ‌گیری مانند Splunk باشد. به هر حال، مقصد نهایی لاگ‌ها می‌تواند توسط محیط اجرایی شما به صورت مستقل از برنامه مدیریت شود.</div>
